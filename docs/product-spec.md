# DSH Desktop 手机远程操控 · 产品方案

> 状态：v0.1 草案（待 review）
> 分支：feature/phone-remote
> 范围：本文只定义「手机远程操控」这个产品方向；原生 app 工程不放在本仓库，单独建仓。

---

## 1. 一句话定位

**不是「付费打洞」，是「手机上完整体验地操控你的 AI coding agent」。**

管道（局域网 / 公网连通）只是载体；订阅费买的是「零配置 + 稳定 + 手机端完整体验（审批、通知、多设备同步）」。

---

## 2. 目标用户与问题

**用户**：正在用 DeepSeek Harness（及同类 coding agent）的开发者，希望人在外面也能推进 / 看管任务。

**问题**：
- agent 跑一个长任务，人不在电脑前，任务卡在「等你审批 / 问你问题」就停住了。
- 任务跑完、出错，没有任何通知，只能回电脑前才知道。
- 想在外面看一眼进度、回一句、批准一步，却没有趁手的入口。

**关键洞察**：真正的痛点是**「agent 跑到一半需要人，而人不在」**，不是「连不上那台电脑」。

---

## 3. 核心价值主张

| 价值 | 说明 |
|---|---|
| **审批 + 通知（灵魂）** | agent 的 ask-user / plan 审批 / 提问 / 完成 / 报错 → 实时推送到手机 → 一键回复继续跑 |
| 零配置配对 | 扫码即连，不装第三方客户端、不登第三方账号 |
| 手机完整体验 | 会话 / 工作区 / goal / 任务 / jobs / 中断，全在手机上做完 |
| 多设备同步 | 手机与桌面看到同一份会话状态 |
| 端到端加密 | 服务端看不到内容（信誉卖点，放免费档） |

---

## 4. 非目标（Non-goals）

- ❌ 云上托管执行 agent（那是 Daytona / Coder / E2B 的战场，另一个量级）。
- ❌ 重新实现 dsh 的 agent 能力（模型、插件、工具全部沿用上游）。
- ❌ 把「打洞/传输」本身作为卖点或付费点。
- ❌ v1 做团队协作 / 多人共享一台 agent 主机。

---

## 5. 免费 vs 订阅

**免费档（局域网）零边际成本**：点对点直连，不经过我方服务器 → 永久免费。
**付费档（公网）有真实成本**：relay 带宽 / 机房 / 推送 / 运维 → 收费。

| 能力 | 免费 | Pro（订阅） |
|---|---|---|
| 局域网远程（同 WiFi） | ✅ | ✅ |
| 公网远程（任何地方） | ❌ | ✅ |
| 扫码配对 | ✅ | ✅ |
| 端到端加密 | ✅（信誉卖点） | ✅ |
| 推送通知（完成/审批/提问/报错） | ❌ | ✅ |
| 多设备 / 会话历史同步 | ❌ | ✅ |
| 手机完整体验（审批/任务/工作区） | ✅ 基础 | ✅ 完整 |

---

## 6. 核心体验闭环（用户旅程）

1. 桌面打开 dsh，点「手机远程」→ 出现二维码。
2. 手机扫码 → 配对完成（公钥交换）→ 进入移动端界面。
3. 手机上新建 / 恢复会话，派任务。
4. agent 跑到一半要批准 → 手机弹通知 → 一键批准 → agent 继续。
5. 任务完成 / 报错 → 手机收到推送 → 回来查看结果。

---

## 7. 产品架构

```
手机端（PWA 先行，原生兜底）
   │  公网：relay + E2E   │  局域网：直连 + E2E
   ▼                      ▼
桌面壳（改造为常驻宿主）── 本地反向代理（token + 密钥）
   │  转发（含 WebSocket/SSE）
   ▼
dsh web  @ 127.0.0.1:3080  ← 安全边界不变
```

### 7.1 桌面端（本仓库，改造核心）

- 现状：启动 splash → `window.location.replace(url)` 把整个壳交棒给 dsh 页面，自己退场。
- 目标：改造成**常驻宿主**——
  - 持续跑本地反向代理（监听局域网端口，含 WebSocket/SSE 转发）。
  - 常驻「远程/配对」面板：开关、二维码、连接状态、token 轮换/撤销。
  - 把服务端推送桥接进本地（Pro 档）。
- 涉及文件：`dsh.go`、`app.go`、新增 `remote.go`、`frontend/src/main.js`、`frontend/index.html`。

### 7.2 手机端

- **PWA 先行**：复用 dsh 现成 Web UI（已是 PWA，有 manifest + viewport），「添加到主屏幕」即用。
- **原生 app 不可省**：主卖点是体验，iOS 推送（APNs）必须原生。**原生工程独立建仓，不写进本目录。**

### 7.3 服务端（Pro 档）

- relay（转发密文）+ 信令 + 账号 + 设备管理 + 推送（APNs/FCM）+ 订阅/支付。
- E2E：服务端只转发密文，看不到内容（详见 7.4）。

### 7.4 E2E 加密与扫码配对

- 扫码即完成密钥交换：手机与桌面各自生成密钥对，二维码携带公钥 / 走 PAKE。
- 服务端为「透明管道」，只转发密文 → 内容不可见，也是合规免责点。
- E2E 是**信誉卖点**，放免费档，不作为付费门槛。

## 9. 阶段路线图

| 阶段 | 内容 | 收费 |
|---|---|---|
| **M1 局域网底座（MVP）** | 反向代理 + token + 扫码配对 + 常驻远程面板 | 免费 |
| **M2 手机体验层** | 审批 / 会话 / 任务移动端体验，PWA 完整体验 | 免费基础 |
| **M3 服务端 + 公网档** | relay + 账号 + 推送 + 多设备同步 + E2E + 支付 | 订阅 |
| **M4 原生 app** | 补 iOS 推送最后一公里，原生体验 | 订阅体验 |

## 10. MVP（M1）范围与验收

**范围**：
- 桌面壳改造为常驻宿主（不再重定向后退场）。
- 新增 `remote.go`：启动/停止反向代理、生成/轮换 token、导出二维码、暴露 Remote 状态。
- 局域网内手机可扫码连入，完整驱动 dsh 会话。

**验收标准**：
- [ ] 同一 WiFi 下，手机扫码后能打开并操控 dsh 会话（含 WebSocket/SSE 实时流）。
- [ ] token 可轮换、可撤销，默认关闭。
- [ ] 桌面壳能显示远程开关 / 二维码 / 连接地址。

| 决策 | 结论 | 理由 |
|---|---|---|
| 手机端形态 | PWA 先行，原生不可省 | 快出体验验证需求；iOS 推送必须原生 |

| 付费点 | 体验，不是打洞 | 打洞被 Tailscale/CF 免费掉 |
| E2E 定位 | 信誉卖点，放免费档 | 不该是付费门槛 |

- **主力用户是国内还是海外？** 直接决定支付通道与公司主体。

## 15. 对标 Codex 的体验基准（北极星）

> 来源：OpenAI《Work with Codex from anywhere》官方能力清单 + 社区对照文档。

### Codex 手机端能做什么（我们必须逐条覆盖）

1. 查看正在进行的线程 / 任务状态。
2. 阅读阶段性输出、终端输出、截图、diff、测试结果。
3. 回复 agent 的进一步提问。
4. 审批命令、网络访问等需要人工确认的操作（**灵魂能力**）。
5. 改变任务方向、切换模型、补充新上下文。
6. 新建任务，让 agent 在已连接的环境里开始工作。

### 决定「像不像 Codex」的体验属性

- 任务实际在原机跑：文件 / 依赖 / 凭据 / 权限 / 本地配置**不搬家**。
- 账号绑定、跨设备会话同步（对应我们 M3 的 relay + 账号）。
- 移动端定位克制：适合「离开电脑但任务不停」；大 diff review、生产环境、密钥、部署这类高风险操作**回电脑做**。
- 典型闭环：桌面派任务 → 离开 → 手机跟进 / 审批 → 回电脑终审。

### 映射到 dsh 能力与我们的阶段

| Codex 能力 | dsh 对应 | 阶段 |
|---|---|---|
| 查看线程 / 任务状态 | session.* / todo / jobs | M1 / M2 |
| 阅读输出 / diff / 终端 | session 事件流（已有 SSE / WebSocket） | M1 / M2 |
| 回复提问 | user-questions / ask-user | M2 |
| 审批操作 | plan-mode / ask-user 权限 | M2（推送 M3） |
| 换方向 / 换模型 / 补上下文 | model selection / prompt | M2 |
| 新建任务 | session create | M1 / M2 |
| 账号跨设备同步 | 无（需自建 relay） | M3 |

### 与 Codex 的关键差距（承认并逐步追平）

- Codex 靠账号中继天然跨设备；我们是 M1 局域网直连，M3 才上账号 + relay。
- Codex 原生 app 推送稳定；我们 M4 原生兜底。
- 差距不在「连不连得上」，在**会话连续性**与**通知闭环**。
